# 1.4.1：授权核验、ColorOS 手动保存、卡片滑动

2026-10-19 用户验收反馈：普通模式未授权 Root 却直接创建闹钟且未打开预期界面；设置中选择 Root 会立刻切模式；希望在下方推荐卡片左右滑动，同步切换上方五种模式。

用户进一步确认：对于这版 ColorOS，接受打开新建页后自己填写推荐时间并保存，优先保证由本人保存。手势为下方卡片左右滑，上方模式同步；不是用上下滚动切模式。

## 原因与修正

1. `StandardClockResolver` 原来已传 `EXTRA_SKIP_UI=false`，普通模式不启动 Root。历史 ColorOS 16.19.14 的 `HandleApiActivity.b0()` 证据显示：带 `HOUR` 就先调用创建路径；`HOUR` 缺失且 extras 非空时，进入打开编辑页分支。故“已创建”不能证明应用获得 Root。
   - 对 `com.coloros.alarmclock / com.oplus.alarmclock.cts.HandleApiActivity`，省略时、分，保留非空 extras 和 `SKIP_UI=false`。
   - 其他时钟保留标准预填；没有增加第二次创建或强制停止时钟的操作。
   - 首页及返回后的确认卡片提醒手动填写目标时间，再保存。实际手机上的编辑页仍须用户验证；本轮没有连接手机。
2. `selectMode(ROOT)` 原来先持久化模式，再做可静默失败的预热。现在先核对兼容性，再在后台用真实 su 申请并核验，只有成功才持久化 Root 模式。
   - 等待期间仍显示普通模式，并暂缓新闹钟请求；可取消。
   - 拒绝、超时、不兼容均保留普通模式并说明原因、管理器授权及重试方式。取消或超时后的迟到结果不能再切回 Root。
   - 保存过的 Root 偏好在进程重启后也需重新核验。实际写闹钟前保留原有的再次核验；发现授权失效时回到普通模式。
   - 系统授权弹窗由超级用户管理器控制。管理器已拒绝或设置不提示时，相位不能强制它弹窗，必须显示失败与手动授权指引。
3. 推荐大卡片增加横向手势，拖动时上方滑块同步预览，松手按位移或速度切相邻模式。首尾不循环；取消手势不提交；垂直滑动交给页面；按钮上的横向拖动不能变成设闹钟点击。

### 原始失败与修正

首次编译发现 libsu 超时参数需要 Long，已修正。首次完整回归 31 项中 9 项失败，原结果保留在 [失败摘要](evidence/initial-failed-summary.json)，不能当作通过：

- 产品侧修正授权完成顺序：结果和偏好先提交，再解除等待状态。
- 测试等待同时覆盖点击尚未被 UI 处理的情况；刷新 API33+ 无障碍缓存，继续断言真正的 selected 状态；滚动统一走页面空白边缘，避免标题滚走后误选内嵌滚轮。
- 共存包与 Android 默认测试程序撞包导致测试程序安装被判降级；仪器包改为 `com.example.smartalarm.instrumentation`，入口同步。最终回归使用这个独立测试程序。
- 一次后台构建启动确认超时，但后续状态证明进程实际已经运行；没有重复启动同一构建，等待其最终 exit 0。未将启动确认的超时算成构建成功。

重复问题的防回归依据见 [疑难杂症笔记](../疑难杂症笔记.md)。

## 手机验收

1. 覆盖安装“相位·测试版”；原版 1.2.0 保留。
2. 普通模式点“设为系统闹钟”：验证 ColorOS 确实打开新建页，手动填推荐时间并保存；不应由本次请求先创建一条。
3. Root 入口：取消确认、拒绝授权时仍为普通；管理器允许后只有核验成功才能进入。若管理器不弹窗，按提示为“相位·测试版”授权后重试。
4. 下方推荐卡片左右滑：上方模式同步；上下滚动浏览内容，不切模式；横滑按钮不设置闹钟。

厂商编辑页、真实超级用户管理器弹窗与授权、Root 实际读写及响铃、真机手势手感尚未重新验证；31 项模拟器结果不替代这些验收。
